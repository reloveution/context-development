Правила работы с планом

**Основные принципы**

- Двигаемся небольшими шагами: один пункт или подпункт за раз — обсудить → сделать → остановиться на ревью пользователя.
- Обсуждаем каждый шаг, задавай вопросы, если что-то неясно.
- Стенс харнесса (`~/.claude/CLAUDE.md` и аналоги) действует всегда; здесь — только то, чего в нём нет.
- Используй любые доступные скилы, когда они помогают.
- Опирайся на документацию установленной версии харнесса (официальные сайты) и ищи в интернете best и bad practice по темам пункта.
- Качество важнее скорости; скорость — за счёт дробления на подпункты, не за счёт глубины.
- Язык плана и отчётов — русский.

**Работа с планом**

- Источник правды — `plan.md`. Идём строго по порядку следования пунктов в файле; при препятствиях или новых вводных обсуждаем корректировку порядка или плана.
- Не разделяй список на параллельные ветки.
- Большой пункт дроби на подпункты (например, по одному на харнесс) и веди их по одному.
- **Блокер:** если пункт требует результата более позднего, не откладываем его, а сразу переносим в плане следом за пунктом-блокером — с прежним номером и заметкой `> после п.M: <что нужно из него>`. Подпункт переносится так же, со своим номером.
- Запрещены временные костыли: вторые копии «на всякий случай», ручные зеркала поверх симлинков, шимы совместимости. Незавершённое должно быть видно — открытый пункт, явная ошибка, битая ссылка, пойманная проверкой (`find -L <папка> -type l`), — а не спрятано.
- Номера существующих пунктов не меняем — на них ссылаются. Новое — подпунктом в родственный пункт или в конец списка.
- Слияние пунктов — только по решению пользователя: ссылки обновить одной правкой и сверить grep-ом; номера влитых пунктов больше не использовать, новое — со следующего свободного (сейчас 41).
- Текст пользователя при переформатировании сохраняем дословно; после перестройки пункта сверяем, что ничего не потерялось (счёт ссылок и строк).

**Отметки о статусе**

- `N [ ]` — предстоит, `N [x]` — выполнено.
- Подпункты — `N.M`, `N.M.K`; отступ — 8 пробелов на уровень. Короткая заметка «почему» — строкой `> …`.
- Зависимость фиксируем один раз: у перенесённого пункта — «после п.M», у пункта, который готовит вход для другого, — «вход для п.N»; обратной пометкой не дублируем.
- Сразу после завершения подпункта отмечай его `[x]` и сжимай до одной строки — краткий итог сделанного.
- **Закрытый пункт не хранит то, что записано в другом месте.** Проверь каждую заметку: факт уже в своём доме — удали; область другого пункта — удали; вопрос разрешился — удали.
- Факт, которого больше нигде нет, не удаляй, а **перенеси в его дом**: механика харнессов и требования к архитектуре — в `harness-layout`; долг — в пункт, который его закроет.
- В закрытом пункте остаётся только живое решение, у которого дома нет: «не делать» или решение за пользователем.

**Исполнение** — обязательно для каждого пункта

1. **Исследование** — до правок: best practice и отдельно bad practice / анти-паттерны по темам пункта.
2. **Доказательства** — поведение харнесса считается фактом только после живого прогона. Документация, схема и бандл — гипотеза; в плане так и помечай («по бандлу», «не проверял»). Пример: `envFile` у cursor CLI есть в схеме, но файл не читается — это показала только проба.
        - проба: ответ есть только в теле проверяемого файла; запуск из пустой папки в `~`, не внутри репо; флаги без интерактива — в п.1; `claude -p` из-под Claude Code — через `env -i HOME=$HOME PATH=$PATH USER=$USER LOGNAME=$LOGNAME …` (без USER и LOGNAME — «Not logged in»).
        - временные пробы (файлы, записи в конфигах, папки проектов в харнессах) убирать сразу после проверки; `rm` с путём из переменных — только в форме `${VAR:?}`.
        - правка скилла — не утверждение о харнессе, проверка локальная: `global/skills/make-skill/scripts/check_skill.py`; фронтматтер — строгим YAML; описание — длина, без «: », триггеры в первых ~100 символах; `find -L` по ссылкам; grep по имени при переименовании и удалении. Новый скилл или новое описание — плюс один прогон в Claude (`claude -p`) на одну фразу-триггер; без базовой линии, повторов, других харнессов и проектов.
3. **Согласованность** — новое повторяет принятую раскладку (`harness-layout`): одна копия — в `global/` и `local/`, в харнессах только симлинки; скилл — короткий `SKILL.md` плюс `references/` по требованию (`make-skill`, Structure); скрипты внутри папки скилла, без `../`; слой задаёт папка — `global/` ядро, `local/coding/<пакет>/` языковой пакет. Отступление — только с названной причиной.
4. **Скрипты** — логика в скриптах (хуки, скрипт подключения из п.38, скрипты скиллов) — с тестом и прогоном; ручная мутационная проверка: точечная правка → тест падает → откат.
5. **Секреты** — значение не должно пройти через контекст агента: файлы с ключами целиком не читать, вывод маскировать, проверять по наличию, префиксу, счёту. Перенос ключей делает пользователь; агент готовит команды и проверяет результат. Секрет живёт в локальном файле вне git (0600), в конфиге — только имя переменной.
6. **Git и необратимое** — git по стенсу. Перед коммитом пользователя агент называет ожидаемое число файлов и проверяет индекс. Необратимое — удаление неотслеживаемого, правка файлов вне репо (`~/.zshrc` и т.п.) — только после явного «да».

**Аудит после пункта** — после работы и отчёта, по порядку, без пропусков

1. `git diff` — в context-development и в каждом затронутом репо харнесса (`git -C ~/.<харнесс> diff`).
2. **Перепроверка** — скилл `recheck` по отчёту и работе: что заявлено, но не сделано; что сделано, но не сказано.
3. **Живая проверка** — проба в каждом затронутом харнессе (правка скилла — проверка из п.2 «Исполнения»), битые ссылки, поиск секретов в том, что уйдёт в коммит.
4. **Исправить** всё найденное в шагах 2–3; по каждой проблеме — снова best/bad practice.
5. **Гигиена плана** — `[x]`, сжатие, перенос фактов в дом.
6. Только потом остановиться и ждать ревью пользователя.

Порог: полный цикл — для пунктов, которые меняют поведение харнессов, конфиги, смысл скиллов и правил. Механические правки (формат плана, переименование, перенос файлов) проходят только шаги 1 и 5.
